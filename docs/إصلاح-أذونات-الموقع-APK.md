# إصلاح أذونات الموقع في APK — التشخيص والحل المضمون

> **الجمهور**: مالك المشروع + فريق التشغيل.  
> **الحالة**: كل الإصلاحات موجودة في المستودع (الكود والسكربتات) — **المطلوب فقط إعادة بناء APK جديد وتثبيته مكان القديم**.  
> **الشكوى الأصلية**: «في بوابة المناديب لا تظهر أذونات النظام للهاتف… تظهر لنا مشكلة تعذر الوصول إلى موقعك الحي، فعّل خدمة الموقع بالجهاز» — في **النسخة المثبتة APK القديمة**.

---

## 0) الملخص السريع (TL;DR)

| السؤال | الجواب |
|---|---|
| هل الكود الحالي معطوب؟ | **لا** — الأذونات والإضافة وواجهات الاسترداد كلها مضبوطة في المستودع. |
| إذن أين المشكلة؟ | الـAPK المثبّت على أجهزة المناديب **بُني قبل** إضافة أذونات الموقع إلى `AndroidManifest` وقبل مزامنة إضافة `@capacitor/geolocation`. |
| ما الحل؟ | إعادة بناء APK عبر GitHub Actions (القسم 2) بتشفير إصدار أعلى ثم تثبيته. |
| كم يستغرق؟ | ~15–25 دقيقة بناء في السحابة + دقيقة تثبيت. لا حاجة لأي بيئة تطوير على جهازك. |

---

## 1) التشخيص — لماذا ظهرت «تعذّر الوصول إلى موقعك الحي»؟

### 1-أ) تسلسل السببية (في النسخة القديمة)

1. تطبيق توفير APK يعمل بنمط **Capacitor Live WebView**: التطبيق الأصلي غلاف يعرض تطبيق الويب الحي من `tawfir.giize.com`. أي أن كود الموقع الذي تعرضه هو **كود المستودع الحالي**، لكن طبقة الأذونات الأصلية (AndroidManifest) تأتي من **لحظة بناء الـAPK** ولا تتحدث تلقائياً.
2. في بوابة المناديب، دائرة النبض `useCourierPulse` (`src/hooks/useCourier.ts`) تراقب الموقع الحي عبر `navigator.geolocation.watchPosition`.
3. داخل WebView لأندرويد، طلب الجيولوكيشن يمر عبر `BridgeWebChromeClient.onGeolocationPermissionsShowPrompt` — وهو **يطلب إذن وقت التشغيل ثم يمنح الـWebView، لكن فقط إذا كان الإذن معلناً في `AndroidManifest.xml` أولاً**.
4. النسخة القديمة من الـAPK بُنيت **قبل** أن يضيف `scripts/patch-android-identity.mjs` إذني `ACCESS_FINE_LOCATION` و `ACCESS_COARSE_LOCATION` — وبالمثل قبل إضافة `@capacitor/geolocation@8` إلى الاعتماديات (مسار النافذة الأصلية).
5. النتيجة: أندرويد **يرفض الطلب صامتاً** (طلب صلاحية غير مصرّح بها في الـManifest = رفض فوري بلا أي نافذة سماح) ← `watchPosition` يفشل ← الواجهة تعرض: «تعذّر الوصول لموقعك الحي — فعّل خدمة الموقع بالجهاز».
6. لهذا كانت الرسالة **مضللة**: خدمة GPS في الجهاز مفعّلة أصلاً — الخلل في غلاف الـAPK لا في الجهاز.

### 1-ب) ما الذي أُصلح فعلاً في المستودع (موجود الآن ويكفي إعادة البناء)

| الطبقة | الملف | ما يفعل |
|---|---|---|
| Manifest | `scripts/patch-android-identity.mjs` (القسم 4-ب) | يحقن `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` + `POST_NOTIFICATIONS` (+ `INTERNET`/`ACCESS_NETWORK_STATE`/`VIBRATE`) في `AndroidManifest.xml` بطريقة idempotent — يعملها تلقائياً أثناء كل بناء. |
| الإضافة الأصلية | `package.json` → `@capacitor/geolocation@^8.0.0` | `npx cap sync android` يسجّلها كمكوّن أصلي داخل الـAPK — نافذة السماح الحقيقية + GPS دقيق. |
| جسر الويب | `src/lib/native-permissions.ts` | `getNativeLocationPosition()` يستدعي `Geolocation.getCurrentPosition` داخل الـAPK فقط (`isNativePlatform`)، مع خرائط أخطاء عربية واضحة (رفض الإذن / GPS معطّل / مهلة) و`checkNativeLocationPermission()` للفحص بلا نافذة. |
| مسار التعافي | `GeoLocationField` + `StoreLocationPicker` + `NativeNotificationsNudge` | نافذة إعادة المحاولة + زر «افتح إعدادات التطبيق» عند الرفض النهائي (القسم 5). |
| iOS | `scripts/patch-ios-identity.mjs` (القسم 2-هـ) | يضيف `NSLocationWhenInUseUsageDescription` إلى `Info.plist` + تحقق ختامي يفشل البناء إن غاب (القسم 4). |

> **خلاصة**: لا عطب في الكود — الـAPK القديم ببساطة «مستقطن في الزمن» قبل هذه الإصلاحات. الـWebView يعرض كوداً جديداً فوق غلاف أندرويد قديم.

## 2) الحل المضمون — إعادة بناء APK عبر GitHub Actions

### 2-أ) الخطوات (مرة واحدة لكل إصدار)

1. افتح المستودع على GitHub: `https://github.com/Moh-abah/tawfir`
2. تبويب **Actions** ← اختر الـworkflow المسمى **«Build Android APK + AAB — توفير»**.
3. اضغط **Run workflow** واملأ المدخلات:

   | المدخل | القيمة | ملاحظات |
   |---|---|---|
   | `app` | `customer` | تطبيق العملاء/المناديب الموحّد. اختر `owner` فقط لبناء تطبيق التاجر المنفصل. |
   | `version_name` | مثلاً `1.3.0` | اسم الإصدار الظاهر للمستخدم (SemVer). |
   | `version_code` | **رقم أكبر من آخر بناء** | ⚠️ أندرويد يرفض التثبيت فوق نسخة لها `versionCode` مساوٍ أو أقل (`INSTALL_FAILED_VERSION_DOWNGRADE`). إن كان آخر بناء `2` فاجعلها `3`. |

4. اضغط زر التشغيل الأخضر وانتظر (15–25 دقيقة). تابع التقدم من صفحة الـrun.
5. عند النجاح: نزّل الـAPK من قسم **Artifacts** بالأعلى — اسمه مثل `tawfir-customer-v1.3.0-3` (يضم APK + AAB + بصمات SHA-256).
6. فك ضغط الملف، انقل `tawfir-customer-v1.3.0-3.apk` إلى الجوال وثبّته:
   - فعّل «التثبيت من مصادر غير معروفة» إذا سأل أندرويد.
   - **التثبيت فوق النسخة القديمة آمن**: نفس مفتاح التوقيع = تحديث نظيف يحافظ على بيانات تسجيل دخول المناديب. (إن رفض أندرويد التثبيت فأزل القديم أولاً ثم ثبّت الجديد.)
7. للنشر على Google Play: ارفع ملف **AAB** (لا APK) مع نفس `version_code` الأعلى.

### 2-ب) الأسرار المطلوبة (غالباً مضبوطة سابقاً — تُفحص مرة واحدة)

من **Settings ← Secrets and variables ← Actions** يجب وجود:

- `ANDROID_KEYSTORE_BASE64` — ملف `tawfeer-release.keystore` بترميز Base64
- `ANDROID_KEYSTORE_PASSWORD` — كلمة مرور الـKeystore
- `ANDROID_KEY_ALIAS` — الاسم المستعار (`tawfeer`)
- `ANDROID_KEY_PASSWORD` — كلمة مرور المفتاح

الـworkflow يفشل مبكراً برسالة عربية واضحة إن نقص أي سرّ — قبل إهدار دقائق البناء.

### 2-ج) ماذا يفعل الـworkflow آلياً؟ (سلسلة الأمان)

```
bun install
→ npx cap add android            (مشروع Android نظيف من الصفر — rm -rf android)
→ npx capacitor-assets generate  (الأيقونات والسبلاش من resources/)
→ bun scripts/patch-android-identity.mjs   ← يحقن أذونات الموقع/الإشعارات + التوقيع + الهوية
→ npx cap sync android           ← يسجّل @capacitor/geolocation كمكوّن أصلي
→ ./gradlew assembleRelease bundleRelease  ← APK + AAB موقّعان
→ تحقق بصمة SHA-256 تطابق assetlinks.json + توقيع AAB (jarsigner)
→ رفع الـArtifacts للتنزيل (تبقى 90 يوماً)
```

الخطوة الحاسمة لأذونات الموقع هي `patch-android-identity.mjs` — لذا **أي بناء جديد يخرج والأذونات داخله بالضرورة**.

## 3) التحقق اليدوي بعد البناء — هل الـAPK يحوي الأذونات؟

### الطريقة 1: أدوات سطر الأوامر (`aapt`)

على أي جهاز فيه Android SDK (أو من داخل GitHub Codespaces):

```bash
aapt dump permissions app-release.apk | grep -i location
```

**الناتج المتوقع:**

```
uses-permission: android.permission.ACCESS_FINE_LOCATION
uses-permission: android.permission.ACCESS_COARSE_LOCATION
```

> إن لم يظهر السطران → الـAPK قديم/معطوب — أعد البناء.  
> بديل إن لم يجد `aapt` في PATH: `$ANDROID_HOME/build-tools/34.0.0/aapt dump permissions …` (أو استخدم `aapt2 dump permissions` / `apkanalyzer manifest permissions`).

### الطريقة 2: من الجهاز نفسه (بلا أي أدوات)

1. **إعدادات** ← **التطبيقات** ← **توفير** ← **الأذونات**.
2. إن ظهر بند **«الموقع»** في قائمة الأذونات → الأذونات مدمجة ✓.
3. بعد أول استخدام للموقع ستظهر خياراته: «مرة واحدة» / «أثناء استخدام التطبيق» / «عدم السماح».

**علامة النسخة القديمة المعطوبة**: بند «الموقع» لا يظهر أصلاً في قائمة الأذونات — لأن أندرويد لا يعرض أذوناً غير معلنة في الـManifest.

### الطريقة 3: من داخل تشغيل الـWorkflow نفسه

خطوة **«🔍 لقطة بنية build.gradle + Manifest + FCM»** تطبع كل أسطر `uses-permission` من الـManifest المولّد في سجل البناء — ابحث فيها عن:

```
uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION"
```

### الطريقة 4: الاختبار الوظيفي على الجهاز

سجّل دخول مندوب موثّق ← الرئيسية الميدانية ← فعّل التوفر ← انبثق نافذة السماح الأصلية للموقع عند أول نبضة ← اسمح بـ«أثناء استخدام التطبيق» ← يجب أن تختفي رسالة «تعذّر الوصول لموقعك الحي» وتظهر إحداثيات النبضة.

## 4) حالة iPhone — الموقع عبر Info.plist

- iOS لا يستخدم AndroidManifest؛ يطلب إذن الموقع عبر مفتاح **`NSLocationWhenInUseUsageDescription`** في `Info.plist` — نص يظهر للمستخدم داخل نافذة السماح.
- **الفحص الفعلي**: `scripts/patch-ios-identity.mjs` (القسم 2-هـ) يضيف المفتاح بطريقة idempotent (يُضاف فقط إن لم يوجد، وينجح البناء عند إعادة التشغيل)، **ويوجد تحقق ختامي يُفشل البناء فوراً إن غاب المفتاح**:
  `if (!finalInfo.includes("NSLocationWhenInUseUsageDescription")) fail("تحقق ختامي: وصف إذن الموقع مفقود")`.
- **نص الوصف المحدّث (إصلاح 2-e)** — يشمل البوابات الثلاث (المندوب + التاجر + العميل):

  > «يستخدم توفير موقعك لتوصيل طلباتك وتحديد موقع متجرك وعرض المتاجر القريبة منك.»

  (النص السابق كان يقتصر على العميل: «نستخدم موقعك لعرض المتاجر والمنتجات القريبة…» — تحديث بسيط داخل السكربت نفسه، لا يغيّر منطق الإضافة).

- **فرق جوهري عن أندرويد**: بدون المفتاح في iOS لا يحدث «رفض صامت» — **التطبيق يُسقط (crash) فور استدعاء الموقع**. لذا أهمية المفتاح حرجة، وتغطيته بالتحقق الختامي تعني أن أي بناء iOS ناجح = المفتاح موجود.
- بناء iOS يتم عبر `.github/workflows/build-ios.yml` بنفس النمط (`cap add ios` ثم `bun scripts/patch-ios-identity.mjs` ثم `cap sync ios`) — ولا يحتاج أي خطوة إضافية لإذن الموقع.
- أذونات iOS الأخرى التي يضيفها السكربت بالعربية: الكاميرا (`NSCameraUsageDescription`)، مكتبة الصور (`NSPhotoLibraryUsageDescription` + `NSPhotoLibraryAddUsageDescription`).

## 5) خطة التعافي داخل التطبيق — زر «افتح إعدادات التطبيق»

### السلوك

أندرويد يعرض نافذة السماح **مرتين فقط**؛ بعد رفضين متتاليين يحجبها نهائياً ولا تظهر مجدداً مهما طلب التطبيق. عندها:

1. الموقع يفشل برمز `permission-denied` (خطأ `NativeLocationError` من `src/lib/native-permissions.ts`).
2. الواجهة (`GeoLocationField` / `StoreLocationPicker` / `NativeNotificationsNudge`) تعرض بطاقة عربية تشرح الموقف + **زر «افتح إعدادات التطبيق»**.
3. الزر يستدعي `openNativeAppSettings()` ← إضافة `TawfirNative.openAppSettings` (Java، يولّدها `patch-android-identity.mjs`) ← `Intent(ACTION_APPLICATION_DETAILS_SETTINGS)` ← تُفتح **صفحة تطبيق توفير في إعدادات النظام** مباشرة.
4. المستخدم يفعّل «الموقع» (ويفضّل «أثناء استخدام التطبيق») يدوياً، يعود للتطبيق، ويضغط **«إعادة المحاولة»** — فتستأنف النبضات فوراً بلا إعادة تشغيل.

> على الويب/خارج الـAPK الدالة `openNativeAppSettings()` ترجع `false` بأمان (no-op) — لا تكسر تجربة المتصفح.

### نفس المسار للإشعارات

عند رفض إذن الإشعارات نهائياً، `NativeNotificationsNudge` يعرض نفس زر «افتح إعدادات التطبيق» ليصل المستخدم لصفحة الأذونات يدوياً.

## 6) أذونات أخرى مرتبطة — الإشعارات `POST_NOTIFICATIONS`

- أندرويد 13+ (API 33) يتطلب إذن **وقت تشغيل** للإشعارات. بدونه: زر «الإشعارات» في صفحة التطبيق بإعدادات النظام يظهر **رمادياً معطلاً** لا يمكن تفعيله إطلاقاً — نفس نمط مشكلة الموقع تماماً.
- المعالجة في الـAPK الجديد (كلها داخل `patch-android-identity.mjs` + الويب):
  1. الإذن يُحقن في الـManifest.
  2. `MainActivity.java` يطلب الإذن تلقائياً عند أول فتح للتطبيق (Android 13+، غير مشروط بضبط FCM).
  3. `TawfirNative.requestNotificationsPermission()` يعرض نافذة السماح الأصلية عند الطلب من الواجهة (داخل WebView لا تعمل `Notification.requestPermission`).
  4. مسار التعافي نفسه: زر فتح الإعدادات عند الرفض النهائي.

**قاعدة عامة**: أي سلوك «معطل/رمادي في إعدادات النظام» أو «رفض صامت بلا نافذة» = إذن غائب من الـManifest = **أعد البناء** بعد التأكد أن السكربت يضيفه.

## 7) جدول أعراض ← أسباب ← حلول

| العَرَض | السبب | الحل |
|---|---|---|
| «تعذّر الوصول لموقعك الحي — فعّل خدمة الموقع بالجهاز» في بوابة المناديب رغم أن GPS مفعّل | APK قديم: `navigator.geolocation` داخل WebView يُرفض صامتاً لأن `ACCESS_FINE/COARSE_LOCATION` غير معلنة في الـManifest | إعادة البناء (القسم 2) — نافذة السماح ستظهر عند أول نبضة |
| لا تظهر **أي** نافذة سماح عند استخدام الموقع نهائياً | (أ) APK قديم بلا إذن Manifest، أو (ب) رفض مزدوج سابق فحجب أندرويد النافذة | (أ) أعد البناء، (ب) زر «افتح إعدادات التطبيق» (القسم 5) |
| بند «الموقع» غائب من قائمة أذونات التطبيق في إعدادات النظام | الإذن غير معلن في الـManifest (APK قديم) | إعادة البناء ثم تحقق بطريقة 2 أو 3 (القسم 3) |
| نافذة السماح ظهرت ثم «رفضت» والإحداثيات لا تصل | رفض نهائي (حجب النافذة) | فعّل الموقع من إعدادات التطبيق يدوياً عبر زر التعافي |
| GPS يعمل لكن ببطء/انقطاع «استغرق تحديد موقعك وقتاً أطول» | ضعف الإشارة داخل المباني (خطأ timeout 15 ث بمعالجة عربية أصلاً) | انتقل لمنطقة مكشوفة وأعد المحاولة — ليست مشكلة أذونات |
| الموقع يعمل في متصفح الجوال لكن لا في الـAPK | مساران مختلفان: المتصفح يطلب الإذن بنفسه؛ الـAPK يحتاج الإذن في الـManifest + الإضافة الأصلية | إعادة البناء (تجلب `@capacitor/geolocation` عبر `cap sync`) |
| زر الإشعارات بإعدادات النظام رمادي/معطل | APK قديم بلا `POST_NOTIFICATIONS` | إعادة البناء — الـAPK الجديد يطلب الإذن عند أول فتح (13+) |
| التثبيت فوق النسخة القديمة يُرفض (`INSTALL_FAILED_VERSION_DOWNGRADE` أو «لم يُحدَّث») | `version_code` الجديد ≤ القديم | أعد التشغيل بـ`version_code` أعلى، أو أزل القديم أولاً |
| iOS: التطبيق يغلق فور طلب الموقع | `Info.plist` بلا `NSLocationWhenInUseUsageDescription` | بناء عبر `build-ios.yml` — السكربت يضيفها آلياً والتحقق الختامي يمنع بناءً بلاها |
| كل شيء يعمل لكن المناديب القدامى يشتكون | أجهزتهم ما زالت على الـAPK القديم | وزّع الـAPK الجديد (WhatsApp/رابط Artifact) واطلب التثبيت فوق القديم |

## 8) أسئلة متكررة

**س: هل يفقد المنديب بياناته عند تحديث الـAPK؟**  
ج: لا — التوقيع واحد (`tawfeer-release.keystore`) فالتثبيت «تحديث نظيف» يحافظ على بيانات التطبيق بما فيها الجلسات.

**س: هل أحتاج تعديل كود لكل إصدار جديد؟**  
ج: لا — فقط `version_name`/`version_code` أعلى في مدخلات الـworkflow (ملف `package.json` يبقى المصدر للرقم الأساسي عبر `sync-version.mjs`، والمدخلات تتفوق في الـAPK).

**س: البوابة القديمة `/courier/login` هل زالت؟**  
ج: لا — توجّه تلقائياً إلى `/login?mode=courier` (شاشة الدخول الموحّدة بتبويب المندوب). ليست مرتبطة بمشكلة الأذونات.

**س: متى يجب تفعيل «الموقع الدائم/في الخلفية»؟**  
ج: غير مطلوب حالياً — دائرة النبض تعمل أثناء انفتاح التطبيق فقط («أثناء الاستخدام» كافية تماماً).
