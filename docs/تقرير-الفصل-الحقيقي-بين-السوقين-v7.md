## ✅ الجواب المباشر على أسئلتك الأربعة الحرجة (بالأدلة الحية — اليوم)

### س1: هل المستخدم السعودي يرى مناطق سعودية؟ → **لا. 100% يمني**

| الدليل | النتيجة الحرفية الحية |
|---|---|
| `GET /api/v1/regions` (بدون توكن) | **22 منطقة = المحافظات اليمنية حصراً** (أبين، أمانة العاصمة، إب… سقطرى). صفر مناطق سعودية |
| مخطط `RegionOut` في openapi | الحقول: `id, name, slug, is_active, created_at` — **لا حقل `country_code` أصلاً** في الجدول |
| `POST /admin/regions` (مخطط `RegionCreate`) | يقبل `name + slug + is_active` فقط — **حتى الأدمن لا يستطيع إنشاء منطقة سعودية** |
| جدول `cities` | **غير موجود نهائياً** — لا يوجد أي مسار `cities` في openapi (199 مساراً فحصتها واحداً واحداً) |

### س2: هل يرى السعودي منشآت سعودية؟ → **يختلط كل شيء — لا فلترة بلد إطلاقاً**

الدليل القاطع (نفّذته اليوم بتوكن العميل السعودي `customer.sa@tawfir.test`):

```
GET /facilities?country_code=966  →  أُعيدت كل المنشآت الـ 21 (المعامل أُهمل صامتاً)
```

والقائمة نفسها تكشف الخلط: **المنشأة السعودية #32 «كافتيريا التجريبي السعودي» بإحداثيات الرياض (24.71, 46.67) ساكنة داخل `region_id=1` = «الجوف» — محافظة يمنية!** — إلى جانب 19 منشأة يمنية.

- سبب الخلط: `/facilities` يقبل فقط `region_id, lat, lng, open_now` (openapi) — **لا يوجد معامل بلد في العقد نفسه**.
- `FacilityOut` لا يحمل `country_code` ولا `currency` — المنشأة «أعمى» عن سوقها.

**الخلاصة**: الفصل الحقيقي موجود في **طبقة واحدة** — «من يدفع كيف؟» (البنود 2-6). كل ما عداه — ما يراه المستخدم على الشاشة من متاجر ومناطق وعملات وعضوية وأجور — **يمني بنسبة 100%** حتى للمستخدم السعودي.

### س4: من أين يأتي السعودي «المدينة»؟ → **من لا شيء — لا يوجد مفهوم مدينة أصلاً**

- لا جدول `cities` (س1)، ولا حقول مدينة في المنشأة (`address` نص حر + lat/lng فقط)، ولا في الطلب (`delivery_address` نص حر + `delivery_lat/lng`)، ولا في التسجيل (`region_id` يمني فقط).
- «المدينة» اليوم = **المنطقة اليمنية المختارة في الهيدر** (`tawfir-region` في localStorage) — والسعودي مجبر على اختيار محافظة يمنية ليستطيع التصفح أصلاً (الاستعلامات معطلة بلا منطقة).

## 🎯 ماذا يعني هذا عملياً؟ (رحلة السعودي الحقيقية اليوم)

1. يفتح التطبيق → يرى منتقي «اختر منطقتك» بـ **22 محافظة يمنية**.
2. يحاول التسجيل → **رفض** لأن رقمه لا يطابق النمط اليمني (مَنَع في الواجهة).
3. حساب يُنشأ له يدوياً → سوقه **يمني 967/YER** افتراضياً (الاختبار الحي user 113).
4. يتصفح → يرى **كل المتاجر اليمنية** مختلطة بمتجر سعودي واحد «مقيم» في الجوف.
5. يقرأ الأسعار → **«ر.ي» في كل الشاشات** (formatCurrency الثابتة).
6. يريد عضوية → «حوّل **3000 ريال يمني** إلى محفظة جيب 780090882».
7. عند الطلب فقط → تظهر له الطرق السعودية (كاش + إلكتروني مويسر SAR) — **اللمسة السعودية الوحيدة**.

## 🏗️ مواصفة «الفصل الحقيقي» الكاملة — كل ما يجب أن يتبعه النظام

> هذه هي القائمة التي نسيتَ أشياء منها — اكتملت الآن من الفحص. تُسلَّم لوكيل الباك اند جاهزة في ملف مستقل: `docs/مهمة-الباك-اند-الفصل-الحقيقي-v7.md`.

### أ) طبقة البيانات (DDL)

```sql
-- 1) بلد المنطقة (الأساس الذي يُبنى عليه كل شيء)
ALTER TABLE regions ADD COLUMN country_code VARCHAR(3) NOT NULL DEFAULT '967';
CREATE INDEX ix_regions_country ON regions(country_code);
-- ثم تعبئة المناطق السعودية (13 منطقة إدارية):
-- الرياض، مكة المكرمة، المدينة المنورة، الشرقية، عسير، القصيم، جازان،
-- نجران، حائل، الباحة، تبوك، الحدود الشمالية، الجوف (السعودية!)
-- ⚠️ تنبيه حرج: «الجوف» اليمنية (id=1) و«الجوف» السعودية اسمٌ متشابه —
--    يجب الفصل بالـ country_code لا بالاسم.

-- 2) بلد المنشأة (نُسخ من منطقتها ثم صار قابلاً للتعديل)
ALTER TABLE facilities ADD COLUMN country_code VARCHAR(3) NOT NULL DEFAULT '967';
-- ترحيل: UPDATE facilities SET country_code = (SELECT country_code FROM regions WHERE id = facilities.region_id);
-- تصحيح خاص: UPDATE facilities SET country_code='966' WHERE id=32;  -- الرياض ليست في الجوف

-- 3) عملة المنتج (مرجع الحقيقة المالي — لا استنتاج من الواجهة)
ALTER TABLE products ADD COLUMN currency VARCHAR(3) NOT NULL DEFAULT 'YER';
-- ترحيل: منتجات المالكين السعوديين (owner.sa user 97) → 'SAR'

-- 4) عملة الطلب (تُثبت لحظة الطلب — لا تتأثر بتغيير عملة المنتج لاحقاً)
ALTER TABLE orders ADD COLUMN currency VARCHAR(3) NOT NULL DEFAULT 'YER';

-- 5) بلد المستخدم — موجود (locale/me) لكن يجب استنتاجه تلقائياً
--    عند التسجيل من بادئة الجوال: 05…/5… → 966 ، 7[01378]… → 967
```

### ب) طبقة العقد (API)

| التغيير | التفصيل |
|---|---|
| `GET /regions` | معامل `country_code` اختياري — بدونه يرجع الكل (توافق خلفي)، به يفلتر. **الاستجابة تضيف `country_code`** |
| `GET /facilities` | معامل `country_code` اختياري (اليوم يُهمل — أثبتُّ ذلك حياً). **`FacilityOut` يضيف `country_code` + `currency`** |
| `ProductOut` | **يضيف `currency`** |
| `OrderOut` | **يضيف `currency`** (تُثبت من عملة المنشأة لحظة الإنشاء) |
| `POST /auth/register` | استنتاج `country_code` من بادئة الجوال + قبول `05XXXXXXXX` و `7XXXXXXXX` |
| `POST /otp/request` | دعم أهداف سعودية `05…` (بوابة إرسال ثانية أو مزود يدعم 966) |
| `GET /membership/info` | يُشتق من بلد المستخدم: سعودي → مبلغ SAR + **مسار دفع مويسر للعضوية** (subscription) بدل «حوّل لمحفظة جيب» |
| `GET /orders/delivery-estimate` | يختار جدول الأجرة من بلد **المنشأة**: `SA_DELIVERY_*` للسعودي و `YE_DELIVERY_*` لليمني (اليوم يطبق جدول اليمن في الرياض — أثبتُّه حياً) |
| `GET /cards` + `CardOut` | بطاقات العضوية مربطة بمناطق — تُفلتر بالبلد تلقائياً عبر مناطقها |
| بحث/قريب مني | `/products/nearby` بصيغته lat/lng سليمة فيزيائياً — لا تغيير |

### ج) المعايير والمتغيرات (قواعد يجب أن يتبعها النظام كله)

1. **مصدر حقيقة السوق** = بلد المستخدم (966/967) للمستخدم المسجل، وبلد **المنشأة** لكل ما يعرض داخل متجرها (الأسعار عملة المنشأة دائماً — سعودي يتصفح مطعماً يمنياً يرى YER ويمني يتصفح مطعماً سعودياً يرى SAR — هذه هي القاعدة الصحيحة تجارياً، عكس الافتراض القديم «السوق يتبع المستخدم في كل شيء»).
2. **العملة تُخزن ولا تُستنتج**: كل مبلغ في الاستجابات يحمل عملته (`currency`) — الواجهة تعرض ما قاله الخادم حرفياً.
3. **الجوال مفهرس ببلده**: التخزين بالصيغة المحلية (05…/7…) + `country_code` — وOTP يوجه لمزود البلد.
4. **العضوية لكل سوق سعر ومسار**: SAR/مويسر للسعودية، YER/محفظة جيب لليمن.
5. **أجور التوصيل والعمولة تتبع بلد المنشأة** من مفاتيح `SA_*` / `YE_*` الموجودة أصلاً.
6. **الضريبة (فرق تشريعي لا يُنسى)**: السعودية = ضريبة قيمة مضافة 15% (عرضها على الفاتورة متطلب ZATCA) — اليمن = لا توجد حالياً. حقل `tax_rate` على مستوى البلد في إعدادات المالية + إظهار سطر «ضريبة» في الفاتورة للسعودي فقط.
7. **المانيفست في الكونسول** (نقطة موثقة في v6 §7): يشتق `market.currency` من بلد مالك المنشأة لا من منطقتها — ترقيع ~10 أسطر على خادمك.

## 🚚 خطة ترحيل البيانات (بترتيب التنفيذ الآمن)

1. **دون توقف**: `ALTER` الأعمدة الافتراضية (`country_code='967'` للكل) → النظام يتصرف كما السابق تماماً.
2. تصحيح المنشأة 32 → `country_code='966'` (+ منطقة سعودية إنشئت «الرياض»).
3. تعبئة منتجات المالك السعودي (user 97) → `currency='SAR'`.
4. إنشاء 13 منطقة سعودية (انتبه لفخ اسم «الجوف» — س1).
5. رفع أعلام `SA_*` في إعدادات المالية إن لم تكن مضبوطة (أجرة أساس/كم/عمولة بالريال).
6. تحديث حسابات الاختبار: `customer.sa` region_id → منطقة سعودية.
